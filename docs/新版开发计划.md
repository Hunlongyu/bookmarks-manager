# 书签管理器新版开发计划

更新日期：2026 年 11 月 3 日

建议先完成可独立使用的整理闭环：导入 → 手动整理与去重 → 检查修复 → 预览 → 备份 → 覆盖写回或 HTML 导出。随后接入共享的 AI 分析、搜索和目录分类，最后实现相似网站推荐。

本计划依据[功能清单](书签管理器功能文档.md)安排开发顺序。功能范围与优先级分开记录：已经确认的 P1、P2 功能仍然保留。当前工程只有基础骨架，本轮更新需求与计划，并制作独立 HTML 交互原型，放在原型目录，业务后端仍待实现。

## 评估结论

| 优先级 | 要交付的能力 | 为什么这样排 |
| --- | --- | --- |
| P0 | 单次会话、配置与缓存基础、HTML 和三浏览器接入、手动整理、去重、快速检查、基础修复、恢复、覆盖写回、结束页与性能。 | 构成完整且可验证的清理工具；数据恢复和写回正确性是后续所有功能的前提。 |
| P1 | 规则内容检查、统一 AI 分析、SEO 与标签复用、AI 搜索、两种目录分类、多套在线与本地模型配置。 | 提升查找和整理效率，依赖已经稳定的任务、元数据、变更预览和恢复机制。 |
| P2 | 基础相似推荐、可选联网搜索推荐、独立搜索服务配置和推荐验证。 | 用户可以先完成已有书签清理；新网站发现可在现有 AI 能力上独立迭代。 |
| P2 最后阶段 | 软件自升级。 | 已确认纳入，按用户要求放在所有书签与 AI 功能之后。 |

Chrome、Edge、Firefox 的直接读取和覆盖写回都属于 P0。可以按适配顺序分批完成，但三个浏览器分别通过验收后，才算完成本计划的 P0 范围。

## 技术难点与先后依赖

| 能力 | 相对工作量 | 主要不确定性 | 实施策略 |
| --- | --- | --- | --- |
| HTML 交换与手动整理 | 中 | 格式差异、层级顺序、重复项处理与备份恢复一致性。 | 先建立真实浏览器导出样本，形成首条可运行流程。 |
| Chrome 与 Edge 直接读写 | 高 | 用户配置、本地与账号书签、存储版本、内部标识、校验和同步元数据。 | 共用必要解析能力，两种浏览器分别做读写往返与恢复验证。 |
| Firefox 直接读写 | 高 | Places 数据库结构、书签与历史数据关系、一致性备份与兼容性。 | 早期单独验证；不能用重建数据库的方式只保留书签。 |
| 网络检查与修复 | 中高 | 反爬、登录、跳转、代理差异、请求取消与误判。 | 先用受控站点验证状态和任务控制，再扩大真实站点样本。 |
| AI 分析与搜索 | 中高 | 页面信息质量、模型差异、重复调用、搜索遗漏与误报。 | 统一页面分析输出，先复用后检索，用固定样本验证实际召回。 |
| AI 目录整理 | 中 | 分类粒度、原目录约束、建议与手动修改冲突。 | 复用现有移动与合并能力，AI 只生成可预览的变更建议。 |
| 外部网站推荐 | 中高 | 候选真实性、来源、服务联网能力和检查失败。 | 先做基础候选验证，再接入可选搜索服务。 |
| 软件自升级 | 中 | 发布资产、签名、进程替换、未输出修改和数据库兼容。 | 使用 Wails 能力，单独验证旧版到新版的真实更新路径。 |

最早应验证浏览器直接写回。Chromium 书签编码包含 ID、GUID、校验和同步元数据，存储实现也存在明文、加密及辅助副本路径；这些源码路径不代表每个已发布浏览器配置都采用相同形式。需要按实际版本和配置识别存储，不能把修改一个固定 JSON 文件作为通用方案。[书签编码源码](https://raw.githubusercontent.com/chromium/chromium/main/components/bookmarks/browser/bookmark_codec.cc)、[书签存储源码](https://raw.githubusercontent.com/chromium/chromium/main/components/bookmarks/browser/bookmark_storage.cc)。

Firefox 的 Places 同时管理书签与历史，因此直接写回需要独立适配并保持非书签数据完整。[Firefox Places 文档](https://firefox-source-docs.mozilla.org/browser/places/index.html)。

本表评估相对工作量，不承诺固定日期。浏览器存储兼容范围确认后再按实际任务估算开发日，避免把三种浏览器的覆盖写回当作简单文件替换排期。

## M0 浏览器读写验证

关联：IN-02、IN-03、OUT-02 至 OUT-06。

1. 为 Chrome、Edge、Firefox 建立独立测试用户配置，记录浏览器版本、配置路径和书签存储形式。测试素材包含目录、重复网址、中文、长标题和特殊字符。
2. 读取并保存原始结构及必要元数据。读取期间来源变化时重新取样，数据库读取采用一致性快照，避免得到混合版本。
3. 关闭浏览器并检查相关后台进程与文件占用。备份必须可以实际恢复，不能仅以“文件复制成功”作为完成条件。
4. 对一个标题、一个 URL 和一个目录位置进行最小修改，按照目标格式写回；重新启动浏览器核对结果及非书签数据。
5. 恢复备份后再次核对。测试异常格式、占用、权限不足、磁盘写入失败与启动后浏览器修复行为。
6. 对实际存在的本地与账号书签范围分别核对；记录浏览器自身同步重新运行后的结果。
7. 固定可验证的适配边界。遇到尚未识别的格式要停止写入并提供 HTML 路径，不盲目试写，也不重新引入扩展方案。

完成条件：三浏览器各有真实读写往返和恢复结果；共享的字段保留规则、目标映射规则及尚未支持的情况写入兼容记录。浏览器只读可用不能算写回验收完成。

## M1 会话与基础整理

关联：BAS-01 至 BAS-03、IN-01、IN-04、IN-05、ORG-01 至 ORG-05、DUP-01、DUP-03、SRCH-01、SAFE-02 至 SAFE-04、OUT-01。

- 当前会话保存工作区书签与目录；配置、分析缓存、明确保存的备份单独持久化。备份固定保存到 `%APPDATA%\BookmarksManager\backups`，启动时异步加载备份列表；重新启动从空工作区开始，不自动恢复上次会话。
- 书签实例使用独立标识。同一 URL 可在不同目录存在多条，不能把 URL 作为书签唯一主键。网页分析与书签实例分开关联。
- 建议使用 SQLite 保存配置以外的结构化数据与缓存；先验证驱动的 Windows 构建、事务、迁移及一致性备份，再固定依赖。
- 导入采用解析、预览、确认应用的流程。来源目录和浏览器系统根角色分别记录，避免后续合并时丢失写回落点。
- 实现添加、编辑、移动、排序、删除和目录合并。对同名目录合并内容，对重复书签采用保留全部、跳过或逐项决定。
- 完全重复、空目录清理和所有批量修改生成明确的变更计划，显示影响范围，先建立备份再执行事务；不实现撤销与重做历史。
- 回收站保存目录子树和原始位置。人工恢复时检查目标位置与当前数据版本，不能覆盖用户后来编辑的内容而不提示。
- 左侧分别提供“写回浏览器”“导出 HTML”和“备份与恢复”，不使用顶部笼统的“输出”入口。HTML 用于浏览器交换；备份只从默认目录列表选择恢复，不提供任意备份文件打开或另存位置。
- 普通搜索和结果筛选只查询当前会话。配置和分析缓存即使保存了旧网址，也不能让旧网址重新出现在工作区。

验收重点：三浏览器导出 HTML 的往返、重复目录策略、含重复 URL 的移动和删除、整个目录的回收与恢复、事务失败不留半次修改、新会话与缓存隔离，以及重启后备份列表自动加载、恢复需主动选择、备份保存失败阻止依赖它的修改。

## M2 检查修复与流畅交互

关联：DUP-02、NET-01 至 NET-04、FIX-01 至 FIX-03、META-01、UX-01 至 UX-04。

### 任务与网络

长任务由 Go 调度，前端调用后取得任务标识，通过查询和合并事件获取进度。队列、请求和重试均有边界；Go 的 context 负责取消传播。前端不承担网页检查和 AI 请求。

统一实现直连、系统代理、自定义 HTTP 或 SOCKS5 代理。全局并发、单域名并发、超时、重试次数和响应大小分别控制，默认值通过实测确定。接入本地模型时保留明确的本机直连策略。

暂停停止派发新工作，允许正在执行的请求收尾；取消主动终止可取消请求，不继续派发，保留已完成结果。事件携带会话、任务和版本信息，避免已取消或旧任务的结果污染当前数据。任务明细可重新查询，事件不作为唯一状态来源。

### 检查与修复

快速可访问检查与内容检查分层实现。只检查可访问性时不强制下载完整页面；选中标题、SEO 或内容分析时，共享一次必要的页面获取。限制正文读取大小，网页内容作为待分析数据，不能变成执行本地操作的指令。

重定向类型与最终访问结果分开存储。例如临时跳转后返回成功，仍保留临时跳转类型；跳转后返回错误，不能仅因存在最终 URL 就建议更新。登录跳转、临时签名地址及混合跳转保守处理。

标题、地址和参数修复先展示前后值。应用时检查书签是否已被用户再次编辑，过时建议重新确认。favicon 先完成软件侧修复；浏览器原生 favicon 回写不作为普通书签覆盖的隐含能力。

保存 SEO 与必要片段，保留原书签标题和 URL，不能用抓取结果无提示覆盖。跟踪参数清理只使用明确规则，未知和重要参数保留。疑似重复复用清理与跳转结果，用户决定保留项。

### 工作区与报告

启动直接进入工作区，不提供引导模式、步骤条、模式切换或模式名称。导入后返回列表，配置通过设置按需完成；未配置 AI 时仍能导入、整理、快速检查和输出。

只开发桌面布局，不安排手机界面。桌面容器与前端均不设置固定尺寸或最小宽高限制。验证窗口从较小尺寸到宽屏之间自由缩放，导航和内容随可用空间伸缩，工具栏与表单换行、长内容独立滚动；验证尺寸只是取样，不作为产品窗口约束。

报告不设常驻导航入口。完成整理、成功写回或导出 HTML 后展示本次报告，分别显示各检查层级及每个目标的实际完成、失败、跳过和未分析范围；写回部分失败时仍留在处理页，方便重试或恢复。报告不生成下载文件。

验收重点：受控服务覆盖正常响应、403、404、DNS 失败、超时、跳转循环、临时与永久跳转、HEAD 不支持和代理失败；验证暂停、取消、只重试失败项及过时修复建议。

## M3 浏览器正式接入

关联：IN-02、IN-03、OUT-02 至 OUT-06，以及全部 SAFE 功能。

读取适配按 Chrome → Edge → Firefox 的实现顺序推进；M0 已提前验证三种存储路线，Firefox 不延后到最后才判断是否可行。

用户先选择最终整理结果以及目标浏览器用户配置，再为每个目标显示目录映射和书签变更。写入只有覆盖模式，目标中未包含于整理结果的可写书签会在预览中列为删除。只替换明确的书签范围，保留目标的系统根结构和非书签数据。

执行前核对读取基线与目标当前状态。有变化时停止原计划并重新显示差异，保留当前整理结果，由用户确认新的覆盖范围；不静默改成合并写入。

建议先完成所选目标的关闭状态检查、格式检查和备份，再逐个覆盖。各目标写入过程单独记录，文件或数据库使用各自适当的事务与替换方式。跨浏览器不得宣称整体原子提交；某个目标失败时停止后续写入，展示已成功、失败及未执行目标，再提供重试或恢复入口。

写入后核对目录、顺序、数量、标题和 URL，浏览器实际重新启动后继续验证。更新浏览器格式、账号书签和同步元数据需按照适配结果处理，不能清空无法理解的字段来让文件“看起来能打开”。

恢复也要求关闭目标浏览器，从默认目录自动加载的列表中选择备份，明确将覆盖哪些当前数据。工作区备份与浏览器备份分别恢复，加载备份列表不会自动执行恢复。

验收重点：三个浏览器分别通过；一个浏览器多个用户配置分别通过；多目标部分成功、预览后目标变化、只读受管理范围、失败后恢复均通过。Chrome 和 Edge 共用实现不能替代分别验收。

## M4 AI 核心功能

关联：NET-05、NET-06、AI-01 至 AI-05、SRCH-02、SRCH-03、CAT-01 至 CAT-03。

### 配置与共享分析

Go 提供模型适配和连接测试，支持在线与本地模型、多套配置保存及手动切换。密钥不进入前端日志或版本库，持久化采用适合 Windows 的保护方式；本地模型通过已有服务连接，不把模型权重打包进单 EXE。

共享页面分析输出页面健康判断、用途摘要、规范化标签、依据和信息不足状态。任务开始前说明需要分析与可复用数量，用户选择范围及是否包含所有页面的深度检查。配置模型后不自动开始分析。

缓存记录输入信息、抓取与分析时间、模型及结果格式版本。同一页面的多条书签共享分析，URL 或内容信息有实质变化时失效；不能因同域名而合并不同页面。用户可主动重新分析，失败任务只补未完成部分。

规则内容检查独立于模型运行。AI 复核、标签和用途提取使用同一个页面分析任务，不按功能拆成多次页面分析。

### 搜索

先从本次书签的标题、URL、SEO、摘要与标签召回，再做用途匹配和排序。关键词与语义检索的具体实现按样本效果选择，不预设必须搭建外部向量数据库。

返回真实书签标识、路径、理由与覆盖说明，支持完整列表和分页。检索结果不得混入历史缓存条目或未收藏的推荐网站。

建立固定的图标站样本，包括标题有 icon、标题无关键词但用途明确、信息缺失以及用途不相关的网站。记录召回、误报和未分析覆盖情况，不用模型生成的“全部找到”作为验收依据。

### 目录整理

实现沿用原分类与重新规划两种模式。AI 读取现有页面分析及选定范围，输出目录与移动建议；由本地规则验证目标是否有效、是否形成循环、是否越过所选范围及是否产生需要处理的重复项。

沿用 M1 的合并、移动、预览和备份恢复能力。用户可调整或只应用部分建议，已手动修改的项目需重新核对，AI 不直接覆盖最新编辑。

验收重点：同一页面健康判断与标签确实共享分析调用；模型失败不影响基础整理；AI 搜索和分类不悄悄重新分析整批页面；两种分类模式均可恢复。

## M5 相似网站推荐

关联：REC-01 至 REC-03。

基础模式读取当前书签已有用途信息，由模型提出候选，再抓取和检查网址及实际用途。结果明确说明候选来自模型已有知识；页面检查来源与真实搜索来源分别标明。

联网模式适配已支持搜索的模型服务或独立搜索 API。联网能力通过接入验证，不能仅因为服务能回答聊天就启用联网推荐。保存服务配置，复用现有代理、超时和任务控制。

推荐面板展示名称、URL、用途、推荐理由、来源、检查时间和已收藏状态。无法确认的用途或条件标为未核实；链接不可访问不能伪装成已验证站点。保存前再次查重，由用户选择目标目录与保存项。

验收重点：基础与联网来源不混淆；无搜索能力、无结果、候选重复、服务失败均有实际结果；关闭面板不会添加书签。

## 发布与自升级

UPD-01 已确认纳入，作为 M6 放在全部业务功能之后完成。实现版本号、GitHub Releases 资产命名与校验信息、更新入口和失败处理；此前不含更新器的版本仍通过手动下载替换升级，不能宣称具有自升级能力。

Wails 提供 app.Updater，能够处理更新源、下载验证、替换与重新启动，支持自定义界面；更新暂存位置需要可写。发布流水线和 AppData 数据迁移仍由项目负责。[Wails 更新文档](https://wails.io/guides/updater/)、[应用自升级教程](https://wails.io/tutorials/04-self-update-a-wails-app/)。

升级流程采用手动检查 → 更新说明 → 确认下载 → 校验 → 重启。重启前处理未输出修改及仍在运行的检查或写回任务；数据库结构变更先备份再迁移，失败保留可恢复数据，不能静默创建空库覆盖原数据。

发布验收覆盖干净 Windows 环境启动、WebView2 环境处理、单 EXE 分发、程序目录权限、更新失败保留可用旧版，以及真实旧版到新版的数据兼容。编译成功不能替代浏览器写回、更新和 UI 验收。

## 性能验收建议

以下数字是实施目标，需在记录过配置的 Windows 测试机上测量。主要使用 1 千、5 千、1 万条样本，包含深层目录、重复项、长 URL 和图标缺失情况。

| 项目 | 建议目标或记录方式 |
| --- | --- |
| 常用交互反馈 | 点击、选择、切换目录及任务控制的前端反馈 p95 不超过 200ms。 |
| 普通本地搜索 | 1 万条样本中首次可见结果 p95 不超过 500ms；AI 服务响应单独记录。 |
| 长任务启动 | 操作后及时展示任务已接受和当前进度，不等待整个导入、检查或分析完成才反馈。 |
| 检查期间操作 | 能持续滚动、搜索、切换目录；记录主线程长任务、卡顿和资源占用。 |
| 暂停与取消 | 分别记录点击反馈、停止派发、请求实际收尾时间；不能把按钮变灰当作任务已停止。 |
| 事件与渲染 | Go 合并进度更新，列表按需渲染，图标按需加载；避免每条结果重建整棵目录树。 |
| 网络与 AI 耗时 | 单独统计外部服务等待，不用网络总耗时衡量前端响应。 |

## 工程边界建议

以下仅用于后续拆任务，本轮不创建业务空接口。

| 模块 | 责任 |
| --- | --- |
| session | 当前工作区、来源、目录与书签实例、版本和选择范围。 |
| storage | 配置与缓存持久化、SQLite 事务、迁移与索引。 |
| changes 与 recovery | 变更预览、确认应用、回收站、备份恢复。 |
| importexport | HTML 解析、导入预览和 HTML 导出。 |
| browser | Chrome、Edge、Firefox 的配置发现、读取、写回、校验和恢复。 |
| jobs 与 network | 有界队列、暂停取消、代理、HTTP 客户端和进度事件。 |
| checker 与 metadata | 可访问与内容规则、重定向、参数、标题、favicon 和 SEO。 |
| ai 与 search | 模型适配、共享页面分析、语义搜索、分类建议与外部推荐。 |
| updater | 在最后阶段封装 Wails 更新流程及发布约定。 |
| frontend | Radix 交互、统一工作区、列表、预览、任务与报告展示。 |

前端通过 Wails 调用服务，长任务立即返回可查询的任务标识。编辑和预览计划带数据版本，执行前检查变化。底层字段和模块名称属于实施建议，可调整，不改变已经确认的产品行为。

## 开始业务开发前的准备

1. 完成 M0 三种浏览器的独立测试配置及读写恢复验证。

独立交互原型放在原型目录，使用实际 React 与 Radix Themes 组件，覆盖统一工作区、直接浏览器读取、覆盖写回、AI 分析复用和自升级演示。原型中的系统与网络操作均为模拟，业务后端按上述阶段实施。
